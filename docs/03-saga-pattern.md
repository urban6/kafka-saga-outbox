# Saga Pattern

Saga는 **여러 로컬 트랜잭션을 연결해 하나의 업무를 처리하는 패턴**이다. 각 단계는 자기 DB에 커밋하고, 이후 실패하면 이미 완료한 작업에 필요한 보상을 수행한다.

## 보상 트랜잭션

보상 트랜잭션은 **이미 커밋한 작업의 효과를 되돌리는 새로운 트랜잭션**이다. 커밋 전 변경을 취소하는 롤백과 다르다.

```text
주문 저장·재고 예약 → 커밋
          ↓
       결제 거절
          ↓
주문 취소·재고 반환 → 새 트랜잭션으로 커밋
```

## 흐름을 조율하는 방식

| 구분 | Choreography(코레오그래피) | Orchestration(오케스트레이션) |
|---|---|---|
| 동작 | 각 서비스가 이벤트에 반응해 다음 작업·보상 결정 | 조율자가 다음 작업·보상을 지시하고 담당 서비스가 실행 |
| 장점 | 단계가 적으면 간단하고 이벤트 구독으로 확장 가능 | 진행 상태와 실패·보상 흐름을 관리하기 쉬움 |
| 단점 | 흐름이 분산되어 추적·변경이 어려워질 수 있음 | 조율자의 상태 관리와 장애 복구가 필요 |
| 의존성 | 이벤트 계약과 업무 흐름에 의존 | 조율자와 명령·결과 계약에 의존 |

이 프로젝트는 **order가 조율자인 Orchestration 방식**이다. 결제 요청을 보내고, 승인되면 주문을 완료하며 거절되면 주문 취소와 재고 반환을 수행한다.

**Outbox는 DB 변경과 메시지 기록을 함께 저장하고, Saga는 여러 단계의 업무 흐름과 보상을 관리한다.**

## 실패 처리와 복구

정상 진행과 보상 작업 모두 실패할 수 있다. 오류 종류에 따라 대응한다.

| 오류 종류 | 예시 | 처리 |
|---|---|---|
| 일시적인 장애 | DB 연결 실패 | 간격을 두고 정해진 횟수나 시간까지 재시도 |
| 확정된 업무 실패 | 잔액 부족으로 결제 거절 | 완료한 작업에 필요한 보상 실행 |
| 처리 결과 불명 | 결제·환불 요청 후 응답 타임아웃 | 실제 결과 조회 또는 같은 멱등성 키로 안전하게 재요청 |

재시도 한도를 초과했다고 업무 실패로 확정하지 않는다. 실패한 단계와 복구에 필요한 상태를 저장하고, 원인 해결 후 미완료 단계부터 재개한다. 자동 복구가 어려우면 관리자에게 알리고 수동으로 복구한다.

**정상 처리와 보상 모두 멱등성이 필요하다.** 예를 들어 재고 반환이 성공한 뒤 응답만 유실되더라도, 재시도로 재고가 두 번 증가하면 안 된다. 같은 DB에서 처리한다면 중복 처리 이력과 재고 변경을 하나의 트랜잭션으로 저장한다.

## DLQ

**DLQ(Dead Letter Queue)는 처리하지 못한 메시지를 별도로 보관하는 곳**이다. Kafka에서는 별도 토픽을 사용하며 DLT(Dead Letter Topic)라고도 부른다.

```text
메시지 처리 실패 → 재시도 → 한도 초과 → DLQ + 알림
                                          ↓
                                   원인 해결 → 재처리
```

실패한 메시지와 오류 정보를 원인 분석과 재처리에 활용한다. **DLQ 이동은 Saga 완료나 복구를 뜻하지 않는다.** 실패를 확인할 담당자와 재처리 절차가 필요하다. 메시지 기반 처리가 아니라면 DB에 미완료 작업을 저장하고 다시 실행할 수도 있다.
