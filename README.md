# Kafka 기반 주문, 결제 분산 트랜잭션 설계 및 장애 검증

주문 서비스와 결제 서비스가 각자의 DB를 가진 MSA 환경을 가정한 프로젝트입니다. 서로 다른 DB에 걸친 작업은 트랜잭션 하나로 묶을 수 없습니다. 이 상황에서 네트워크 장애, 메시지 중복, 결제사(PG) 응답 지연이 생겨도 **돈과 주문 상태가 어긋나지 않도록** 설계하고, 장애를 직접 만들어 검증했습니다.

## 요약

- 주문 접수, 결제, 재고 확정까지의 흐름을 Kafka 메시지로 연결
- 메시지가 유실되지 않도록 Outbox 패턴과 Debezium(CDC) 사용
- 같은 메시지가 여러 번 와도 한 번만 처리되도록 모든 수신 지점에 중복 방지 적용
- 결제사 응답이 늦어 결과를 모르는 결제는 성급하게 판단하지 않고, 나중에 조회해서 확정
- 아무 에러 없이 멈춘 주문을 찾아내는 감시 배치 구현
- 결제사 장애, 응답 지연, 깨진 메시지, 메시지 발행 중단을 직접 만들어 결과 확인

## 이 프로젝트가 지키려는 것

모든 설계는 아래 네 가지를 지키기 위한 것입니다.

1. 고객의 돈이 빠졌다면 그 주문은 반드시 완료된다
2. 한 주문에 돈이 두 번 빠지지 않는다
3. 재고는 초과 판매되지 않고, 취소된 주문이 잡아둔 재고는 반드시 돌아온다
4. 문제가 생긴 주문이 아무도 모르게 방치되지 않는다

## 서비스 구성

| 서비스 | 역할 |
|--------|--------|
| order (8081) | 주문 접수, 재고 관리, 전체 흐름 조율 |
| payment (8082) | 카드 등록, 결제 승인, 결제사 연동 |
| Mock PG | 결제사 흉내. 실패율과 응답 지연을 원하는 대로 설정 가능 |

두 서비스는 서로의 DB를 보지 않고 Kafka 메시지로만 대화합니다. 실제 결제사 테스트 환경은 일부러 장애를 일으킬 수 없어서, Toss 빌링 API 규격을 따르는 Mock PG를 만들어 썼습니다.

## 주문 흐름

1. 고객이 카드를 한 번 등록합니다. 결제사가 발급한 빌링키를 저장합니다
2. 고객이 주문하면 order가 주문 저장, 재고 예약, 결제 요청 메시지 기록을 한 트랜잭션으로 처리하고 곧바로 "접수됨(202)"을 응답합니다
3. payment가 결제 요청 메시지를 받아 결제사에 청구합니다
4. payment가 결과(승인 또는 거절)를 메시지로 order에 알립니다
5. 승인이면 order가 재고를 확정하고 주문을 완료합니다. 거절이면 재고를 되돌리고 주문을 취소합니다
6. 고객은 주문 조회 API로 결과를 확인합니다

## 설계하며 고민한 것

### 1. DB 저장과 메시지 발행이 둘 중 하나만 성공하면?

주문을 DB에 저장하고 Kafka로 결제 요청을 보내는 코드는 두 작업이 따로 성공하거나 실패할 수 있습니다.

- 메시지는 나갔는데 DB 저장이 실패하면, 없는 주문에 대해 돈이 빠집니다
- DB 저장은 됐는데 메시지 발행 전에 서버가 죽으면, 주문이 영원히 결제 대기로 남습니다

**해결:** 메시지를 Kafka에 직접 보내지 않고, 주문과 같은 트랜잭션으로 `outbox` 테이블에 기록합니다(Outbox 패턴). 그러면 둘 다 저장되거나 둘 다 취소됩니다. 실제 발행은 Debezium이 DB 변경 로그를 읽어서 대신 합니다.

### 2. 같은 메시지가 두 번 오면?

위 방식은 메시지 유실은 막지만, 장애 상황에서 같은 메시지를 두 번 보낼 수 있습니다. 결제 요청이 두 번 처리되면 이중 결제가 됩니다.

**해결:** 받는 쪽마다 "이미 처리한 메시지" 기록을 남깁니다. 이 기록은 실제 처리와 같은 트랜잭션에서 저장해서, 처리는 됐는데 기록이 안 남는 틈이 없게 했습니다. 결제사 호출에도 주문번호를 멱등키로 보내 결제사 쪽에서 한 번 더 막습니다.

### 3. 고객이 주문 버튼을 두 번 누르면?

**해결:** 주문 API는 요청마다 고유한 `Idempotency-Key` 헤더를 필수로 받습니다. 같은 키로 다시 오면 새 주문을 만들지 않고 처음 주문을 돌려줍니다. 동시에 들어와도 DB 유니크 제약으로 하나만 통과합니다. 같은 키에 내용이 다른 요청은 클라이언트 버그로 보고 거부합니다(422).

### 4. 여러 단계에 걸친 흐름을 누가 책임지나?

주문, 결제, 재고 확정이 서로 다른 서비스에서 일어나면 중간에 멈췄을 때 "지금 어디까지 왔는지"를 아는 주체가 필요합니다.

**해결:** order가 흐름 전체를 조율합니다(오케스트레이션 사가). 주문마다 진행 상태를 테이블에 기록하고, 결제 결과에 따라 다음 행동(재고 확정 또는 재고 반환과 주문 취소)을 결정합니다. 상태 변경은 "지금 이 상태일 때만 바꾼다"는 조건부 UPDATE로 해서, 늦게 도착한 중복 메시지가 상태를 되돌리지 못하게 했습니다.

### 5. 결제사가 응답하지 않으면 돈이 빠진 건가?

결제 연동에서 가장 사고가 많이 나는 지점입니다. 응답이 타임아웃되면 결제가 됐는지 안 됐는지 알 수 없습니다.

- 실패로 처리하면: 실제로는 돈이 빠졌는데 주문이 취소됩니다
- 다시 청구하면: 이중 결제가 될 수 있습니다

**해결:** 결제사 응답을 "돈이 빠졌는가"를 기준으로 네 가지로 나눴습니다.

| 결제사 응답 | 돈 | 처리 |
|--------|--------|--------|
| 승인 | 빠짐 | 승인 알림 |
| 카드 거절 | 안 빠짐 | 거절 알림, 재고 반환, 주문 취소 |
| 일시적 오류 (500, 처리 중) | 안 빠짐 | 잠시 뒤 재시도 |
| 타임아웃, 처음 보는 에러 | 모름 | 판단을 미루고 나중에 결제사 조회 API로 확인 |

"모름"인 결제는 order에 아무것도 알리지 않습니다. 틀린 알림은 되돌릴 수 없기 때문입니다. 별도 배치가 결제사에 결제 결과를 물어보고, 확인된 결과로 확정합니다. "이미 처리된 결제"라는 응답도 실패가 아니라 성공으로 처리합니다.

### 6. 에러 없이 조용히 멈추면?

Debezium이 멈추거나 알림 메시지가 사라지면 에러 로그조차 남지 않습니다. 주문은 결제 대기 상태로 계속 남습니다.

**해결:** 일정 시간 넘게 진행되지 않은 주문을 주기적으로 찾아 알람을 냅니다. 알람 기준은 멈춘 주문 개수가 아니라 **가장 오래 멈춘 주문의 경과 시간**입니다. 개수는 트래픽에 따라 오르내리지만, 경과 시간은 정상이면 0이고 문제가 있으면 계속 커집니다.

### 7. 끝내 처리하지 못한 메시지는?

형식이 깨진 메시지나 재시도를 다 써도 실패한 메시지는 기본 설정에서 그냥 버려집니다. 그러면 나중에 원인을 찾거나 다시 처리할 수가 없습니다.

**해결:** 이런 메시지를 별도 토픽(DLT)에 원본 그대로 보관합니다. 깨진 메시지 하나가 뒤따르는 정상 메시지를 막지 않도록 역직렬화 실패도 따로 처리했습니다. 카드 거절 같은 정상적인 실패는 DLT로 보내지 않습니다.

### 8. 같은 재고를 여러 주문이 동시에 잡으면?

**해결:** 재고 차감은 "남은 수량이 충분할 때만 차감"하는 조건부 UPDATE 한 문장으로 처리합니다. 한 주문에 여러 상품이 있으면 항상 상품 ID 순서로 잡아서, 서로 다른 순서로 잡다가 교착 상태(데드락)에 빠지지 않게 했습니다.

### 9. 쌓이기만 하는 기록은?

`outbox`, 처리한 메시지 기록, 주문 멱등키 기록은 계속 쌓입니다.

**해결:** 오래된 기록을 주기적으로 지웁니다. 처리한 메시지 기록은 Kafka 메시지 보관 기간보다 오래 남겨서, 오래된 메시지가 다시 와도 새 메시지로 착각하지 않게 했습니다. 한 번에 많이 지우면 DB 락이 길어지므로 조금씩 나눠 지웁니다.

## 장애 상황 검증

Mock PG 설정과 Debezium 정지로 장애를 직접 만들어 확인했습니다.

| 상황 | 결과 |
|--------|--------|
| 정상 결제 | 요청 한 번으로 1초 안에 주문 완료 |
| 카드 거절 | 재고가 원래대로 돌아오고 주문 취소 |
| 같은 주문 요청 3건 동시 전송 | 주문 1건, 청구 1건 |
| 결제사 오류 50% | 재시도 13회 발생, 주문 6건 모두 완료, 재고 오차 0 |
| 결제사 오류 100% | 6번 시도 후 DLT에 보관. 결제 기록 없이 주문은 대기 상태로 남고 감시 배치가 발견 |
| 결제사 응답 5초 지연 (타임아웃 3초) | 타임아웃 후 판단 보류. 결제사는 2초 뒤 승인했고, 53초 뒤 배치가 조회해서 승인으로 확정. 주문 완료 |
| 같은 메시지 재전송 | 한 번만 처리 |
| 깨진 메시지 | DLT에 원본 그대로 보관, 뒤따르는 메시지는 정상 처리 |
| Debezium 정지 | 65초 뒤 알람, 재개하자 1.2초 만에 주문 완료, 알람 해제 |

## 테스트

- 단위 테스트는 도커 없이 수 초 안에 끝납니다 (`./gradlew build`)
- 통합 테스트는 Testcontainers로 실제 MySQL과 Kafka를 띄워 돌립니다 (`./gradlew integrationTest`)
- 테스트 메서드 기준 단위 34개, 통합 51개
- 테스트용 스키마를 따로 두지 않고 운영 DDL을 그대로 사용합니다
- Mock PG는 실제 HTTP로 호출해 타임아웃 상황을 그대로 재현합니다
- 코드를 일부러 망가뜨렸을 때 테스트가 실제로 실패하는지도 확인했습니다

## 구현 중 발견한 문제

- 한 주문에 여러 상품을 담으면 재고를 잡는 순서가 요청마다 달라 데드락이 날 수 있었습니다. 상품 ID 순서로 고정하고, 순서가 보장되는 타입만 쓰도록 컴파일 단계에서 강제했습니다
- 주문 멱등키 저장에 `INSERT IGNORE`를 쓰면 긴 키가 잘린 채 저장되어, 앞부분이 같은 서로 다른 요청이 하나로 합쳐졌습니다. 일반 INSERT와 중복 키 예외 처리로 바꿨습니다
- Spring Kafka 4에서 DLT 토픽의 기본 이름 규칙이 바뀌어 첫 실행에서 발행이 실패했습니다. 버전에 따라 바뀌지 않도록 이름을 코드에서 고정했습니다
- 같은 DB 안에서 테이블마다 시각이 UTC와 한국 시간으로 섞여 저장되고 있었습니다. 동작에는 문제가 없지만 테스트 데이터를 테이블마다 맞춰 넣어야 했습니다

## 남은 과제

- 결과를 모르는 결제를 조회했을 때 "결제 기록 없음"이면 지금은 실패로 확정합니다. 결제사가 아직 처리 중이라 조회에 안 보이는 경우라면, 돈은 빠졌는데 주문이 취소될 수 있습니다. 같은 멱등키로 다시 요청해서 결과를 맞추도록 수정할 예정입니다
- 결제사 장애가 재시도 시간(약 10초)보다 길면 메시지가 DLT로 갑니다. 장애 동안 메시지 처리를 멈추는 방식과 DLT 재처리 도구가 필요합니다
- 결제 금액을 결과 알림 단계에서 다시 대조하지 않습니다
- 결제 서비스의 모니터링 지표, 정산 대사, 결제 취소와 환불은 아직 없습니다

## 실행

```bash
docker compose up -d

# 토픽 생성 (자동 생성을 꺼 두었습니다)
docker exec kop-kafka bash -c '
for t in payment.commands order.saga.replies order.events \
         payment.commands.DLT order.saga.replies.DLT; do
  kafka-topics --bootstrap-server localhost:29092 \
    --create --topic $t --partitions 3 --replication-factor 1
done'

# Debezium 커넥터 등록
for s in order payment; do
  curl -X POST -H 'Content-Type: application/json' \
    --data @docker/connect/$s-outbox-connector.json localhost:8083/connectors
done

./gradlew :order:bootRun
./gradlew :payment:bootRun
```

```bash
# 카드 등록 (끝자리 0000 카드는 항상 거절됩니다)
curl -s localhost:8082/api/payments/billing-keys -H 'Content-Type: application/json' \
  -d '{"customerId":"C-1","cardNumber":"1234567812345678"}'

# 주문
curl -s localhost:8081/api/orders -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"customerId":"C-1","items":[{"productId":"P-1001","quantity":2}]}'

# 결과 조회
curl -s localhost:8081/api/orders/{orderNo}
```
