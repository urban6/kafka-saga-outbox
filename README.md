# Kafka로 연결한 주문·결제 서비스

주문과 결제 서비스가 각자의 DB를 사용하는 환경에서, 주문 접수부터 결제와 재고 확정까지 구현한 프로젝트입니다. 서비스 간 작업을 하나의 DB 트랜잭션으로 처리할 수 없어서 Kafka 메시지로 흐름을 연결했습니다.

주로 다룬 문제는 장애가 났을 때의 처리입니다. 주문은 저장됐는데 결제 요청을 보내지 못하거나, 결제는 승인됐는데 응답을 받지 못하면 어떻게 복구할지에 초점을 맞췄습니다. Outbox와 Debezium으로 메시지를 발행하고, 중복 처리 방지와 결제 결과 조회 배치를 구현했습니다. Mock PG의 오류율과 응답 시간을 바꿔가며 실제 주문 상태가 어떻게 바뀌는지도 확인했습니다.

설계할 때 기준으로 삼은 것은 다음 네 가지입니다. 아직 해결하지 못한 부분은 아래의 [남은 과제](#남은-과제)에 정리했습니다.

- 결제가 승인된 주문은 완료까지 이어질 것
- 같은 주문을 중복으로 결제하지 않을 것
- 재고를 초과 판매하지 않고, 취소한 주문의 예약 재고는 반환할 것
- 처리가 멈춘 주문을 찾아낼 수 있을 것

## 서비스 구성

| 서비스 | 역할 |
|--------|--------|
| order (8081) | 주문 접수, 재고 관리, 전체 흐름 조율 |
| payment (8082) | 카드 등록, 결제 승인, 결제사 연동 |
| Mock PG | 장애 재현용 결제사 서버. 실패율과 응답 지연 설정 가능 |

두 서비스는 서로의 DB에 접근하지 않고 Kafka 메시지로 요청과 결과를 주고받습니다. 결제사의 테스트 환경에서는 원하는 시점에 장애를 내기 어려워, Toss 빌링 API 규격을 따르는 Mock PG를 만들어 사용했습니다.

## 주문 흐름

1. 고객이 카드를 등록하면 payment가 결제사에서 발급받은 빌링키를 저장합니다.
2. 주문 요청을 받은 order는 주문 저장, 재고 예약, 결제 요청 메시지 기록을 한 트랜잭션으로 처리하고 `202 Accepted`를 반환합니다.
3. payment가 메시지를 받아 결제사에 청구하고, 승인 또는 거절 결과를 order에 전달합니다.
4. order는 승인된 주문의 재고를 확정하고 주문을 완료합니다. 거절된 주문은 예약 재고를 반환하고 취소합니다.
5. 고객은 주문 조회 API로 처리 결과를 확인합니다.

결과를 알 수 없는 결제는 바로 승인이나 거절로 처리하지 않습니다. 별도 배치에서 결제사에 조회한 뒤 결과를 전달합니다.

## 주요 설계

### 주문 저장과 메시지 발행

주문을 DB에 저장하는 작업과 Kafka로 결제 요청을 보내는 작업은 따로 실패할 수 있습니다. 메시지만 발행되면 존재하지 않는 주문에 결제가 진행되고, DB 저장만 성공하면 주문이 결제 대기 상태에 남습니다.

이 사이의 유실을 막기 위해 Outbox 패턴을 적용했습니다. 주문과 결제 요청 메시지를 같은 트랜잭션에서 DB에 저장하고, Debezium이 DB 변경 로그를 읽어 `outbox`에 기록된 메시지를 Kafka로 발행합니다.

### 중복 메시지와 중복 주문 요청

Outbox를 사용해도 장애 복구 과정에서 같은 메시지가 다시 전달될 수 있습니다. 각 수신 지점에서는 처리한 메시지를 기록하고, 같은 메시지가 오면 건너뜁니다. 처리 결과와 중복 방지 기록은 같은 트랜잭션으로 저장합니다. 결제사 호출에는 주문번호를 멱등키로 보내 중복 청구를 방지합니다.

고객이 주문 버튼을 여러 번 누르는 경우도 별도로 처리합니다. 주문 API는 `Idempotency-Key` 헤더를 필수로 받고, 같은 키의 요청에는 처음 생성한 주문을 반환합니다. 동시 요청은 DB 유니크 제약으로 중복 생성을 막습니다. 같은 키로 주문 내용이 다르게 들어오면 `422`를 반환합니다.

### 주문 흐름과 상태 관리

주문이 중간에 멈췄을 때 어디까지 처리됐는지 확인할 수 있도록, order가 전체 흐름을 조율하는 오케스트레이션 사가를 사용했습니다. 주문별 진행 상태를 테이블에 남기고, 결제 결과에 따라 재고 확정 또는 재고 반환과 주문 취소를 진행합니다.

상태를 바꿀 때는 현재 상태를 조건으로 둔 UPDATE를 사용합니다. 늦게 도착한 중복 메시지가 이미 완료된 상태를 되돌리지 않도록 하기 위해서입니다.

### 응답을 받지 못한 결제

타임아웃이 발생했다고 결제가 실패한 것은 아닙니다. 결제사는 승인했지만 응답만 늦어졌을 수 있습니다. 이때 주문을 취소하면 결제와 주문 상태가 어긋나고, 새 결제를 요청하면 중복 청구의 위험이 있습니다.

그래서 결제사 응답을 다음과 같이 나눠 처리합니다.

| 결제사 응답 | 처리 |
|--------|--------|
| 승인 | order에 승인 결과 전달 |
| 카드 거절 | 거절 결과 전달 후 재고 반환, 주문 취소 |
| 재시도 가능한 오류 코드 또는 처리 중 응답 | 잠시 뒤 재시도 |
| 타임아웃 또는 분류하지 않은 오류 | 결과를 보류하고 결제사 조회 API로 확인 |

결과가 불확실한 결제는 `IN_DOUBT` 상태로 남기고, order에 결과를 보내는 것도 보류합니다. 복구 배치가 결제사에 조회해 결과를 확정한 뒤 전달합니다. 이미 처리된 결제라는 응답을 받았을 때도 거절로 처리하지 않고, 조회로 기존 결과를 확인합니다.

### 멈춘 주문 감지와 실패 메시지 보관

Debezium이 멈춰 결제 요청이 전달되지 않으면, 애플리케이션에 에러가 없어도 주문은 계속 대기 상태에 남을 수 있습니다. 이를 찾기 위해 일정 시간 이상 진행되지 않은 주문을 주기적으로 확인하고 알람을 냅니다.

알람 기준은 가장 오래 멈춘 주문의 경과 시간입니다. 대기 주문 수는 트래픽에 따라 달라지지만, 경과 시간으로는 특정 주문이 오래 방치되고 있는지 확인할 수 있습니다.

재시도를 모두 소진했거나 형식이 잘못된 메시지는 별도 토픽인 DLT(Dead Letter Topic)에 원본을 보관합니다. 나중에 원인을 확인하고 재처리할 수 있도록 남겨두는 용도입니다. 역직렬화에 실패한 메시지도 DLT로 보내 뒤따르는 정상 메시지의 처리를 막지 않게 했습니다. 카드 거절처럼 처리 결과가 확정된 경우는 DLT 대상에서 제외합니다.

### 재고 동시성

여러 주문이 같은 상품의 재고를 예약할 수 있으므로, 남은 수량이 충분할 때만 차감하는 조건부 UPDATE를 사용합니다. 한 주문에 여러 상품이 있으면 상품 ID 순서로 재고를 잡습니다. 요청마다 잠금 순서가 달라져 생기는 데드락을 피하기 위한 조치입니다.

### 기록 보관과 정리

`outbox`, 메시지 처리 이력, 주문 멱등키는 보관 기간이 지난 기록을 주기적으로 삭제합니다. 메시지 처리 이력은 Kafka 메시지 보관 기간보다 오래 유지해, 과거 메시지가 다시 전달돼도 중복 여부를 확인할 수 있게 했습니다. 삭제 작업은 DB 잠금이 길어지지 않도록 소량씩 나눠 처리합니다.

## 장애 재현 결과

Mock PG의 실패율과 응답 지연을 조정하고, Debezium을 중지해 확인한 결과입니다. 아래 시간과 횟수는 해당 실행에서 관찰한 값입니다.

| 상황 | 결과 |
|--------|--------|
| 정상 결제 | 요청 한 번으로 1초 안에 주문 완료 |
| 카드 거절 | 재고가 원래대로 돌아오고 주문 취소 |
| 같은 주문 요청 3건 동시 전송 | 주문 1건, 청구 1건 |
| 결제사 오류 50% | 재시도 13회 발생, 주문 6건 모두 완료, 재고 오차 0 |
| 결제사 오류 100% | 6번 시도 후 DLT에 보관. 결제 기록 없이 주문은 대기 상태로 남았고 감시 배치가 감지 |
| 결제사 응답 5초 지연 (타임아웃 3초) | 타임아웃 후 결과 보류. 결제사는 2초 뒤 승인했고, 53초 뒤 배치가 조회해 승인으로 확정한 후 주문 완료 |
| 같은 메시지 재전송 | 한 번만 처리 |
| 형식이 잘못된 메시지 | DLT에 원본 그대로 보관, 뒤따르는 메시지는 정상 처리 |
| Debezium 정지 | 65초 뒤 알람, 재개하자 1.2초 만에 주문 완료, 알람 해제 |

## 테스트

테스트 메서드 기준으로 단위 테스트 34개, 통합 테스트 51개가 있습니다.

| 명령어 | 내용 |
|--------|--------|
| `./gradlew build` | 단위 테스트와 빌드. Docker 없이 실행 가능 |
| `./gradlew integrationTest` | Testcontainers로 MySQL과 Kafka를 실행하는 통합 테스트. Docker 필요 |

통합 테스트에서는 애플리케이션과 같은 DDL을 사용합니다. Mock PG도 실제 HTTP로 호출해 타임아웃을 재현합니다. 일부 코드를 의도적으로 잘못 수정한 뒤, 관련 테스트가 실패하는지도 확인했습니다.

## 구현 중 발견한 문제

- 여러 상품의 재고를 예약할 때 요청마다 처리 순서가 달라 데드락이 발생할 수 있었습니다. 상품 ID 순서로 고정하고, 순서를 보장하는 타입을 받도록 변경했습니다.
- 주문 멱등키를 `INSERT IGNORE`로 저장하면 긴 키가 잘려, 앞부분이 같은 서로 다른 요청이 하나로 취급됐습니다. 일반 INSERT를 사용하고 중복 키 예외를 처리하도록 바꿨습니다.
- Spring Kafka 4의 DLT 기본 토픽 이름이 생성해 둔 이름과 달라 첫 실행에서 발행에 실패했습니다. 토픽 이름을 코드에 명시했습니다.
- 같은 DB에서도 테이블마다 UTC와 한국 시간이 섞여 저장되고 있었습니다. 테스트 데이터를 넣을 때 각 테이블의 시간 기준을 맞춰야 했습니다.

## 남은 과제

- 결제 결과 조회에서 "결제 기록 없음"을 받으면 현재는 실패로 확정합니다. 결제사가 아직 처리 중이어서 조회되지 않은 경우라면, 나중에 결제가 승인돼도 주문은 취소될 수 있습니다. 같은 멱등키로 다시 요청해 결과를 확인하는 방식으로 보완할 예정입니다.
- 결제사 장애가 재시도 시간인 약 10초보다 길어지면 메시지가 DLT로 이동합니다. 장애 중 메시지 처리를 일시 중지하는 방식과 DLT 재처리 도구가 필요합니다.
- 결제 결과를 전달받는 단계에서 결제 금액을 다시 대조하는 검증은 아직 없습니다.
- 결제 서비스의 모니터링 지표, 정산 대사, 결제 취소와 환불은 구현하지 않았습니다.

## 실행

```bash
docker compose up -d

# 토픽 생성 (자동 생성을 꺼 두었습니다)
docker exec kop-kafka bash -c '
for t in payment.commands order.saga.replies order.events \
         payment.commands.DLT order.saga.replies.DLT; do
  kafka-topics --bootstrap-server localhost:29092 \
    --create --topic $t --partitions 3 --replication-factor 1
done'

# Debezium 커넥터 등록
for s in order payment; do
  curl -X POST -H 'Content-Type: application/json' \
    --data @docker/connect/$s-outbox-connector.json localhost:8083/connectors
done

./gradlew :order:bootRun
./gradlew :payment:bootRun
```

```bash
# 카드 등록 (끝자리 0000 카드는 항상 거절됩니다)
curl -s localhost:8082/api/payments/billing-keys -H 'Content-Type: application/json' \
  -d '{"customerId":"C-1","cardNumber":"1234567812345678"}'

# 주문
curl -s localhost:8081/api/orders -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"customerId":"C-1","items":[{"productId":"P-1001","quantity":2}]}'

# 결과 조회
curl -s localhost:8081/api/orders/{orderNo}
```
